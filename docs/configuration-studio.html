Vyavsetu Configuration Studio

A controlled product builder for layouts, design tokens, dynamic forms, categories and module visibility — designed so each change targets the correct app, tenant and store.

Existing demo protectionThe Studio is a separate page and has its own namespaced browser storage. It does not read or write the existing POS/customer/store/driver app data. Its “Publish” action creates a local test snapshot only — no live app is connected.

What an admin can configure

The product is flexible through an approved registry of components and actions, not arbitrary code execution.

◈

Design system

Semantic colours, approved themes, typography scale, spacing/radius tokens, logo variants and contrast validation.

▤

Page builder

Add, hide, reorder and configure registered hero banners, category grids, product carousels, notices, shortcuts and summary cards.

☷

Dynamic form builder

Text, phone, email, numeric, dropdown, multi-select, switch, checkbox and date fields with schema versioning and validation.

▦

Catalog & category manager

Build category hierarchies, order them, connect products and decide on which supported surfaces categories appear.

⊞

Module visibility

Configure allowed navigation and feature visibility while keeping permissions, plan entitlements and data access enforced by the server.

↶

Publish, version & rollback

Drafts remain private; validated publish creates an immutable version, audit event and rollback path.

Target the right surface

The config resolver must scope settings so one app or tenant never accidentally changes another.

🛍️

Customer App

Home sections, consumer catalog visibility, product cards and supported profile/checkout fields.

🧾

POS Terminal

Quick actions, allowed extra fields, category shortcuts and layout density — never alter billing invariants.

🏪

Store App

Order-list presentation, supported operational fields and allowed menu visibility.

🛵

Driver App

Task-card fields, help content and supported checklist forms.

📊

Business Admin

Dashboard widgets, navigation order, report shortcuts and tenant-owned forms.

🛡️

Super Admin

Global templates and allowed plan capabilities; tenant data access remains separately permissioned and audited.

Safe change lifecycle

A user-created draft never becomes live until the authoritative service validates and publishes it.

1

Draft

Select tenant, store and target surface. Only editable draft state changes.

2

Validate

Check schema, registered components, permissions, entitlements and app-version compatibility.

3

Preview & review

Preview phone/tablet/desktop, review the diff and see affected surfaces.

4

Publish snapshot

Persist an immutable version, audit log and outbox event in one transaction.

5

Notify clients

WebSocket/STOMP signals a new version; REST remains the source of truth.

6

Resolve runtime

Clients fetch the authorized snapshot and use a compatible cached version offline.

7

Observe

Track config version, render failures and schema compatibility without logging personal form values.

8

Rollback

Publish a new release pointing to a known-good snapshot; keep audit history.

Configuration must not become arbitrary code

The component registry is the safety and maintainability boundary.

Allowed through configurationRequires engineering
Change supported text, colour tokens, section order, category visibility and approved fields.New business operation, payment behaviour, domain rule or data-processing capability.
Select registered action keys, approved routes, asset IDs and known data resources.Arbitrary URL fetching, script/HTML execution, SQL or Dart/Java source injected by an admin.
Enable an entitled module's presentation in an authorised surface.Granting permissions, bypassing a subscription gate or accessing another tenant's data.
Publish a schema version after compatibility validation.Breaking stored form responses or old clients without a migration/compatibility plan.

Roadmap after the demo

Keep every stage isolated, feature-flagged and documented before moving to the next surface.

01

Sandbox prototype

Standalone UI, namespaced local storage, surface preview, section/form/category/module editing and local snapshot history. No application integration.

02

Contract and database

Approve inheritance/scope rules, JSON schema registry, PostgreSQL migrations, immutable config versions and audit/outbox structure.

03

Spring Boot API

Implement draft/read/validate/publish/rollback endpoints with tenant authorization, optimistic concurrency, idempotency and security tests.

04

Admin API adapter

Swap sandbox repository for API-backed drafts behind a feature flag; do not change the existing runtime apps yet.

05

First read-only runtime

Integrate one surface first and render only approved components. Contract tests must prove other tenants and surfaces are unaffected.

06

Forms and categories

Add backend-validated form submissions, catalog visibility and compatibility/version migration rules.

07

Offline POS and remaining apps

Use last-known-good config in Drift cache, then roll out POS, Customer, Store, Driver and Admin with rollback drills.
